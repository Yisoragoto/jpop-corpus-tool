# 分词器基准

迁移到 Rust 的唯一真风险是分词器。这份文档记录基准是怎么建的、
验收标准是什么、以及为什么这些数字是可以接受的。

## 为什么需要换分词器

当前 `tokens.pos` 存的是 **UPOS**（`NOUN` / `VERB` / `ADJ`…），由 GiNZA
（spaCy + SudachiPy + 神经网络句法模型）产出。Rust 侧没有 GiNZA，
只有 Sudachi 系（sudachi.rs / Lindera / Vibrato），它们产出的是
**日语词性六元组** `('名詞','普通名詞','一般','*','*','*')`。

所以需要一张桥：`tokenizer/pos_map.py`。

## 这张表是实证推导的，不是拍脑袋

把 8,443 行歌词用 SudachiPy 重新分词，按**字符区间**和库里 GiNZA 的结果对齐
（可对齐 47,173 个 token，占 80.5%），统计每个日语词性对应的 UPOS 分布。

粒度选择：

| 粒度 | 条目数 | 准确率 |
|---|---|---|
| 词性前 1 级 | 16 | 81.32% |
| **词性前 2 级** | **36** | **91.40%** ← 采用 |
| 词性前 3 级 | 46 | 91.67% |
| 前 2 级 + 上一词词性 + 末字 | 4,050 | 93.77% |

第 3 级只多 0.27 个百分点；加上下文特征只多 2.37 个百分点，表却膨胀 100 倍。
**在 209 首歌的语料上那是过拟合**，换个歌手就不成立。选前 2 级。

两条人工覆盖（样本太少，众数是噪声）：

* `感動詞,フィラー` → INTJ（样本仅 5 个，众数 NOUN 20%）
* `記号,一般` → SYM（样本仅 2 个，众数 NOUN 100%）

## 实测结果

```
可对齐              80.46%
分词边界一致(全部)    69.67%   ← 含标点，两个分词器切法本就不同
分词边界一致(实词)    98.16%   ← 有意义的指标
lemma 一致          99.41%
UPOS 一致           91.39%
『是否实词』一致      97.70%   ← 决定 Anki / 词频选中哪些词
```

**为什么「全部」只有 69.67% 但不用担心**：Sudachi 比 GiNZA 多切出 4,073 个
token，几乎全是标点和空白，而这些在词频统计和 Anki 导出里一律被排除
（`IGNORED_POS`）。只看实词部分，边界一致率是 98.16%。

**剩下的 8.6% UPOS 差异是什么**：全部是上下文依赖，查表原理上做不到。

```
409  名詞,普通名詞      GiNZA=ADV   → 映射后=NOUN   名词作状语
404  名詞,普通名詞      GiNZA=ADJ   → 映射后=NOUN   名词作定语
391  名詞,普通名詞      GiNZA=VERB  → 映射后=NOUN   サ变名词
230  動詞,非自立可能    GiNZA=AUX   → 映射后=VERB   「て+いる」的いる
171  形容詞,非自立可能  GiNZA=AUX   → 映射后=ADJ    「ない」作助动词
```

这是放弃神经网络句法分析器要付的价，而且付得起——它影响的是品詞下拉框的
粒度，不影响一个词能不能被找到（`是否实词` 一致率 97.70%）。

## 验收标准

`python scripts/export_tokenizer_baseline.py` 产出 `benchmark/`：

| 文件 | 内容 |
|---|---|
| `ginza_reference.jsonl` | 库里现有分词结果，迁移后要尽量复现的目标 |
| `sudachi_reference.jsonl` | SudachiPy 在同样文本上的结果 |
| `baseline.json` | POS 映射表 + 验收阈值 + 环境信息 + 文件校验和 |

**两级验收，严格程度不同：**

1. **`sudachi.rs` vs `sudachi_reference.jsonl` —— 应该接近 100% 一致**
   （阈值 0.99）。同一个词典、同一个算法，差得多就说明词典版本或
   SplitMode 不对。这是最灵敏的探针，也是主要验收标准。
2. **`sudachi.rs + pos_map` vs `ginza_reference.jsonl`** —— 跨分词器比较，
   阈值取自 SudachiPy 实测水平减去余量。这是「迁移后语料一致性」的度量，
   不是对错判定。

阈值全部写在 `baseline.json` 里，Rust 测试直接读，不用抄。

`baseline.json` 还记了环境（`sudachipy 0.6.11` / `sudachidict_core 20260116`）
和两个 jsonl 的 sha256——换词典版本重新导出时能立刻看出基准变了。

## 验收结果（已通过）

`rust/crates/jp-tokenizer` 用 sudachi.rs v0.6.11（官方 git，非 crates.io 上那个
非官方转发）复现，直接复用 venv 里 SudachiPy 的 `sudachi.json` 和 `system.dic`。

```
第一级：62701/62701 逐 token 一致 = 1.0000（阈值 0.99）
  行 token 数不一致：0/8443

第二级（对齐 47173 token / 8443 行）：
  UPOS 一致        0.9139  阈值 0.894
  『是否实词』一致   0.9770  阈值 0.967
  lemma 一致       0.9941  阈值 0.989
  实词边界一致      0.9816  阈值 0.952
```

**第一级是 1.0000——62,701 个 token 的 surface / lemma / normalized /
reading / 六级词性 / UPOS 全部逐字段相同，8,443 行没有一行 token 数不一致。**
迁移的最大技术风险到此消除。

关键前提是复用同一份配置。`sudachi.json` 里的 `inputTextPlugin`
（尤其是把 `〜` 归一成 `ー` 的 ProlongedSoundMarkPlugin、
以及去振假名的 IgnoreYomiganaPlugin）会改变分词结果，
只给同一个 `system.dic` 是不够的。

跑法：

```bash
cd rust && cargo test --release -- --nocapture
```

缺 `benchmark/*.jsonl` 时测试自动跳过并提示先跑导出脚本，
克隆仓库的人不会因为缺 14MB 夹具看到一片红。

## 迁移后 tokens 表怎么办

现有的 58,628 个 token **不需要重新分词**：它们是 GiNZA 产出的，保持原样即可。
映射表只用于迁移后新导入的歌曲。

代价是新旧歌曲的 POS 会有 8.6% 的体系差异。两个选择：

* **保持现状**：老歌保留 GiNZA 的 UPOS，新歌走 Sudachi + 映射表
* **全库重跑**：用 Sudachi + 映射表重新分词全部 8,443 行，换取完全一致

lemma 一致率 99.41% 说明重跑对词元的影响极小，所以「全库重跑」是安全的。
建议在迁移完成、Rust 侧跑通验收之后再决定。

## 交互路径的 POS 词表 bug（已修复）

`dialogs/song_manager.py` 的交互路径（点歌词查词、振假名）走 SudachiPy，
返回**日语词性**；而 `gui.py` 的 `_lookup_candidates` 按 **UPOS** 分支：

```python
if pos == "VERB":            # 传进来的是「動詞」，永远不成立
if pos in {"ADJ", "ADV"}:    # 传进来的是「形容詞」，永远不成立
```

于是形容词/副词的查词增强分支全部静默失效。

**修法**：token 同时带两个字段——`pos` 是日语词性（界面直接显示它，
`song_manager.py:1638`），`upos` 是 UPOS（供逻辑分支用）。两者不能混。
GiNZA 兜底路径用 `token.tag_.split("-")[0]` 产出日语词性，
和 Sudachi 那条路径对齐（以前它直接放 `token.pos_`，两条路径词表不一致）。

**修复过程中发现 POS 不匹配一直在掩盖另一个 bug。** `_lookup_candidates`
的 VERB 分支里有一句 `add(base + "する")`，对任何含汉字的 base 都追加。
本意是处理サ変名词（勉強 → 勉強する），但进到该分支说明已经是动词、
lemma 本身就是辞书形，结果造出「忘れるする」「見るする」。
只传对 POS 而不修这个，全语料会多出 7,000+ 个垃圾候选。

实测依据（全语料 56,475 个 token）：

| | 变化的 token | 新增候选命中词典 | 查无此词 |
|---|---|---|---|
| 只改 POS 传参 | 7,272 (12.88%) | — | 大量 |
| 再删 `base + "する"` | 538 (0.95%) | — | 仍有「探する」 |
| 再把守卫改成 `len>2` | **325 (0.58%)** | **345** | **0** |

最后一步是因为改用 UPOS 后动词从 `pos != "VERB"` 分支（守卫 `len>2`）
挪进了 VERB 分支（守卫 `len>1`），把「探し」「消し」这类す动词误当成サ変。
两个分支的守卫必须一致。

最终效果全是真改进：

```
287  いい    [ADJ] +良い
 15  よい    [ADJ] +良い, いい      （「よかった」的 lemma）
 12  たまに  [ADV] +たま
  1  勝手に  [ADV] +勝手
```

回归测试在 `tests/test_word_lookup.py`（无 Qt 环境自动跳过）。
